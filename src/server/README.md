# Server modules

Server-only logic, one folder per module: identity, people, sites, workforce, payroll, business, billing, revenue, projects.

- Code here must never be imported by client components. Start each file that touches secrets with `import "server-only";`.
- The Supabase secret key (`SUPABASE_SECRET_KEY`) is read only by `supabase/admin.ts` (`createAdminSupabase()`). It bypasses RLS, so prefer the user's own client (`createServerSupabase()` from `src/lib/supabase/server.ts`) and scope admin queries to an organisation yourself.
- Validate every input with Zod at the boundary. Table changes are audited by database triggers in the same transaction; record app-level events (for example `pii.reveal`) with `rpc("log_audit", ...)`.
- Identity (`identity/`): `getSession()` / `requireAppAccess(href)` read the signed-in user, their memberships and the active organisation (httpOnly `mo_org` cookie, honoured only for the user's own manager memberships). Pages, layouts and shell slots use `getPageSession()` (and `requireAppAccess`, `lookupWorkerPageSession()` / `requireWorkerPageSession()` for the worker app), which read the user from `auth.getClaims()` (a local JWT check) to save a call to the Auth server; memberships and roles are still read live under RLS. Server Actions, Route Handlers and anything that writes use the verified `getSession()` / `lookupWorkerSession()` (`auth.getUser()`); `tests/unit/identity/page-session-boundary.test.ts` enforces it. Every Server Action that writes goes through `mutate()` in `identity/mutate.ts`: role check, Zod parse, then the write with the user's own client so RLS applies; the database triggers audit the row change in the same transaction, and `event` adds an app-level entry through `log_audit`. Multi-row or money writes belong in one SQL function called from `run()`.
- Team (`identity/team.ts`, `team-actions.ts`, `team-invite-lookup.ts`, slice 1.12): Settings > Team lists the active company's managers (`public.team_members`, which reads sign-in emails from Auth, owner and admin only) and pending `membership_invites`. `inviteSpec`, `resendSpec`, `cancelSpec`, `changeRoleSpec` and `removeSpec` go through `mutate()` (owner, admin) and call `create_membership_invite`, `resend_membership_invite`, `revoke_membership_invite`, `change_member_role` and `remove_member`, which enforce the rules for every client: one manager role per invite, only owners grant, change or remove admin, finance and HR (owner decision, 19 Nov 2026; admins handle operations and line managers; every owner is emailed by `notifyOwnerGrantedRole` when someone gets one of those roles), no own role change or removal, owners never changed here (slice 1.13), workers and client approvers left to People. Signed-in users have no direct update or delete on `memberships` or delete on `membership_invites`. Raw tokens exist only in the create and resend results; the action emails the link (`email/team.ts`) and shows it to the inviter only when the email did not go out. Role-change and removal notices are sent with `after()` to the address the function returns. The join page (`/join/[token]`) reads the invite through `membership_invite_lookup` with the secret key (`team-invite-lookup.ts`); accepting uses the user's own client (`accept_membership_invite`) and sets the active company cookie; signing up from an invite takes the address from the invite, never the form, creates no company and asks for no password: it sends an email link (`signInWithOtp`), and after it the join page asks for a password before accepting whenever the session came from an email link (`sessionUsedPassword`, the token's `amr`; slice 1.13). `safeNextPath` allows `/join/<token>` so sign-in and the confirmation link come back to the invite. Refusals arrive as SQLSTATE `MLTM1` (already a member), `MLTM2` (a worker's login), `MLTM3`-`MLTM5` (invite used, expired, cancelled), `MLTM6` (own membership), `MLTM7` (owner), `MLTM8` (not a manager), `MLTM9` (invite email cap: 50 per company, 20 per inviter in 24 hours); `team.ts` maps them to plain English. The invite link is shown to the inviter only when the send was skipped (no Resend key outside production), never after a failed send; names that look like a web address are left out of team emails (`emailDisplayName`).
- Personal data (`crypto/pii.ts`, `people/pii-access.ts`): NIN, bank account numbers and RSA PINs are stored as `bytea` in `_enc` columns with a `_last4` sibling (`bank_account_last4`, `rsa_pin_last4`) so lists never decrypt. Write with `sealPii(value, ctx)` (returns `{ enc, last4 }`, `enc` ready for supabase-js) or `encryptPii` / `encryptPiiForDb`; read with `decryptPii(value, ctx)`, which accepts a Buffer or PostgREST's `\x…` hex text. `ctx` is `{ organisationId, table, column, rowId }` and is bound into the GCM tag, so a value moved to another column, row or organisation will not decrypt: generate the row id with `crypto.randomUUID()` before the insert, and re-encrypt (never copy bytes in SQL) when a value moves. A value that waits elsewhere before reaching its column is encrypted for its destination from the start: a bank-detail change holds the new account number encrypted for `workers.bank_account_enc` of its worker, which is what lets the database apply it when the hold ends. AES-256-GCM, random IV per value, key version byte first; the key is `PII_ENCRYPTION_KEY` (32 bytes, base64), read on first use and nowhere else, failing closed with `PiiKeyError` when missing. Show masked values with `src/lib/mask.ts` (`maskAccount`, `maskRsaPin`, `maskPhone`, `maskNin`, `ninStatus`). Unmask only through `revealPii({ organisationId, field, entity, entityId, reason })`, which takes the role from the session's membership in that organisation, reads the `_enc` column itself with the user's RLS client (`workers` or `bank_detail_changes`, filtered on id and organisation), checks `canSeePii(role, field)` (owner and hr: all; finance: bank account only; everyone else masked) and writes a `pii.reveal` audit row before returning the value. `src/server/crypto` may be imported only from `src/server/` (ESLint and `tests/unit/pii-key-boundary.test.ts`).
- People (`people/`, slice 1.3): `createWorker`, `updateWorker`, `addPayRate`, `cancelPayRate` and `endEmployment` in `people/workers.ts` (Zod schemas in `people/schemas.ts`) go through `mutate()` with roles owner, admin and hr. Multi-row writes are SQL functions running as the caller (`public.create_worker`, `public.add_pay_rate`, `public.cancel_pay_rate`, `public.end_employment`), so RLS and column grants still apply; each takes `p_organisation_id` (the active organisation from the mutate context) and touches only that organisation's rows, so a user with a role in two companies can't act on the other one's workers. Personal data is sealed with `sealPii` for the worker's row id (generated with `crypto.randomUUID()` before the insert). Money is sent to the database as strings of whole kobo, never JavaScript numbers, and read back the same way: select kobo columns cast to text (`basic_kobo::text`, `annual_rent_declared_kobo::text`) and convert with `koboFromText` (`people/pay-rates.ts`; `listPayRates` returns a worker's versions as `bigint` kobo). Never read a kobo column as the raw `number` the generated types suggest. A blank staff ID gets the next free ID in the company's pattern (`people/staff-id.ts`, default `EMP-0001`); a staff ID never changes once saved (no update grant) and is never reused, even after the worker leaves. The database enforces the rest: pay-rate versions in force are never updated except to close `effective_to` (a change is a new version from today or later, and `add_pay_rate` closes the previous one the day before); a scheduled version can have its amounts changed or be cancelled (`cancel_pay_rate`, latest version only, which reopens the version before it) but never moved, and the end of a version followed by another can't change, so versions never leave a gap; no overlapping versions; no pay rate before the start date; one line manager (`line_manager_worker_id` or `line_manager_membership_id`, never both, no loops); `needs_pay_details` kept up to date by trigger (bank details missing, or no rate in force on the later of today and the start date; payroll still resolves the rate as of each pay date); bank columns not updatable by signed-in users (slice 1.7 approvals); `memberships.worker_id` not updatable by signed-in users (slice 1.9 sets it at invite acceptance); and a `workers.personal_data` audit row naming which personal data fields changed, never the values. Database refusals arrive as SQLSTATE `MLPR1`-`MLPR3` (pay rates), `MLLM1`/`MLLM2` (line manager) and `MLAS1` (assignment client); `workers.ts` maps them to field errors.
- Bank-detail changes (`people/bank-changes.ts`, slice 1.7): bank details never change directly. `requestBankChange` (owner, admin, hr; a worker for themselves from slice 1.10) inserts a pending `bank_detail_changes` row; `decideBankChange` (owner, hr, finance) approves, rejects, or stops it during the hold; `withdrawBankChange` lets the requester take it back. The database enforces the two-person rule for every client (trigger, plus check constraints `approved_by <> requested_by` and `rejected_by <> requested_by`), refuses anyone deciding a change to their own bank details, sets `applies_after = decided_at + 72 hours`, and copies the request onto `workers.bank_*` only when it moves approved -> applied after the hold. That move is made by pg_cron every 5 minutes, by `applyDueBankChanges` before a page shows bank details (it writes, so it checks the user with the verified `getSession()` first even on a page rendered from `getPageSession()`), and by the daily `/api/cron/bank-detail-changes` route (Vercel Cron, `CRON_SECRET` bearer), which also emails workers whose change applied. Payouts must read `public.worker_bank_details_as_of(org, worker, at)`, which is right whether or not the apply has run. Payouts must read it as owner, hr or finance (or with the secret key); anyone else gets 42501 rather than a silent fallback to the worker row. `create_worker` always turns a new worker's bank details into a pending request, on every path (Add employee, the import, a direct call), and signed-in users can't insert the `workers` bank columns. On approval, `decideBankChange` decrypts the request and refuses it if its last four digits don't belong to its number, or if it changes nothing: the database can't check that without the key. Emails (`people/bank-change-notices.ts`) go to approvers when a request is raised and to the worker on approval and when it applies, at the worker's current email and every address the record held from 90 days before the request (an editor can change the email alone); an applied notice is marked sent only after it went, so failures are retried for 7 days; they read with the secret key (approvers' addresses are in Supabase Auth), name the account by its last four digits only, and log failures by error name only. Refusals arrive as SQLSTATE `MLBK1` (requester deciding), `MLBK2` (own bank details), `MLBK3` (hold), `MLBK4` (already decided or edited), `MLBK5` (employee left) and `MLBK6` (a signed-in user inserting a worker row that carries bank details).
- Bank file and release (`payroll/payouts.ts`, `payroll/release.ts`, `payroll/bank-formats/`, slice 5.4): owner and finance make an approved run's bank file. The server reads `payout_plan` with the secret key (the only caller that gets encrypted account numbers), decrypts each number in memory, refuses a last-4 mismatch by name, renders the format (generic CSV first, escaped with `csvCell`, naira from kobo by integer division), hashes it, stores it in the private `payroll-files` bucket, then records it with `make_payout_batch` as the signed-in user, which re-checks every item against the details in force (no number ever reaches a table, a log or an error). `payout_file_download` audits a download and gives the path the server signs for 60 seconds. `release_payroll_run` (owner or finance, never anyone who prepared or changed the run, with an active file) moves approved -> released, then `onPayrollReleased` runs `RELEASE_FOLLOW_UPS` (5.5's publication). `worker_bank_details_as_of` returns `bank_code` too.
- People import (`people/import/`): `validatePeopleImport(file, context)` checks a CSV or `.xlsx` employee file and returns, per row, a normalised worker, pay rate and mapping or the problems holding it back. Pure: existing workers, managers, departments, clients, projects and sites are passed in as plain data; it never reads or writes the database. Each row's `raw` cells and `normalised.worker` carry NIN, bank account number and RSA PIN in clear: read those fields to encrypt them before storing. Both objects mask them in `JSON.stringify`, `console.log` and Sentry (a non-enumerable `toJSON` and `util.inspect` hook), but a spread copy loses that, so never log one. Amounts above ₦1,000,000,000 per cell, staff IDs outside `[A-Za-z0-9][A-Za-z0-9._/-]{0,39}` (after NFKC) and text starting with `=`, `+`, `-` or `@` are held back. Regenerate the 162-row fixture with `pnpm fixtures:people`.
- CSV downloads (formula injection): any CSV built from typed or imported values, starting with "Download problems (.csv)" in slice 1.8, is written with `formatCsv()` from `people/import/csv.ts`, which prefixes a cell starting with `=`, `+`, `-`, `@`, tab or carriage return with `'` so Excel shows it as text. The importer also refuses those characters at the start of names and staff IDs, but the writer's escape is the defence that applies to every export; each new export adds a test that a `=1+1` cell comes out as `'=1+1`.
- People import flow (`people/imports/`, slice 1.8): `startImportSpec`, `checkImportSpec`, `applyImportFixSpec`, `commitImportSpec` and `cancelImportSpec` in `batches.ts` (Server Actions in `actions.ts`), owner, admin and hr. The browser uploads the file straight to the private `imports` bucket at `{organisation_id}/{batch_id}.{csv,xlsx}` (insert only for the batch's creator while it is `uploaded`; only the uploader can read it back); the server reads it, validates it with `people/import/`, stores every row with `save_import_check` and removes the upload. In `import_rows`, `raw` and `normalised` never hold NIN, bank account number or RSA PIN (check constraints); those sit in `*_enc` columns encrypted for the import row (`rows.ts`). Every later check (a one-click fix, a commit) works from the stored rows plus the decrypted personal data, against the account as it is then; a fix's patch always comes from a fresh check, never from the form or the stored review. Commit (`commit_import_batch`, one transaction, `statement_timeout` 300s for large files) gets only rows that import, managers before reportees, with personal data re-encrypted for each new worker's id; it creates new department, client, site and project names once, the workers (through `create_worker`), first pay rates and assignments, marks the rows imported and logs `people.import_committed`. Re-sending rows already imported does nothing; a partly imported payload is refused (`MLIM1`). Fixes are logged as `people.import_row_fixed` (row, fix label and columns, never values). Downloads: `/app/people/import/template` and `/app/people/import/{batch}/problems` (through `formatCsv`). Uploads never outlive their use: the check removes the file however it ends (a check that throws records `check_unfinished` on the batch, which stays `uploaded`), and a later check, commit and cancel remove anything left. `save_import_check` takes `p_final` and `rows_expected`: a batch moves to `validated` only on the last chunk with every row stored, so a check that stopped part way is never reviewed or imported (a re-check from the file keeps the stored row ids). Signed-in users only read `import_rows`; it is written by `save_import_check`, `commit_import_batch` and `cancel_import_batch` through role-checked security definer functions in `private`. Commit and cancel clear the rows' encrypted personal data (`*_enc`); held rows keep it until imported. What the server never got to is handled by `people/imports/sweep.ts`: `/api/cron/contract-documents` (Vercel Cron, daily, `Authorization: Bearer $CRON_SECRET`, 404 without a configured secret of 16+ characters) removes, with the secret key, every upload of a batch past `uploaded` or still `uploaded` after an hour, and pg_cron (`private.expire_import_batches`, hourly) cancels batches still `uploaded` after 24 hours and clears their personal data. Storage refuses deletes in SQL, so files are only ever removed through the Storage API.

- Owners (`identity/owners.ts`, `owner-notices.ts`, actions in `team-actions.ts`, slice 1.13): a company can have several owners. `requestOwnerChangeSpec` (owners) and `decideOwnerChangeSpec` (the database decides who) call `public.request_owner_change` and `public.decide_owner_change`: with one owner, adding an owner (an existing manager, or an invite) happens at once; with two or more, adding, removing and demoting an owner (stepping down included) waits in `public.owner_changes` for a different owner (insert-only, `approved_by <> requested_by`). The last owner can't go (`MLOW1`) and workers never become owners. An owner invite is a `membership_invites` row with role `owner` and `owner_change_id`; its raw token exists only in the request or approval result, and the action emails it like a team invite. `notifyOwnerChange` / `notifyOwnerJoined` email every owner with a confirmed address (plus a removed or demoted owner) with `after()`, reading addresses with the secret key; names that look like web addresses are left out. Refusals `MLOW1`-`MLOW7` map to plain English in `src/lib/owners.ts`.
- Passwords (`identity/invite-password.ts`, `password-actions.ts`, `email-link-limit.ts`, slice 1.13): a password counts only once chosen after the address was confirmed, from an email-link session (`app_metadata.password_set_at >= email_confirmed_at`, written with the secret key by `markPasswordChosen`; `passwordTrusted` in `src/lib/auth/amr.ts`, `private.password_trusted` in SQL). Owner sign-up and the join page send email links (`signInWithOtp`) and ask for the password afterwards; `/set-password` handles everyone else; password sign-in with an untrusted password signs out and emails a link; `accept_membership_invite` refuses untrusted passwords (`MLPW1`). After a password is chosen, `chooseOwnPassword` ends the account's other sessions (`public.end_other_sessions` and Supabase's sign-out of others; both failing fails the action), records `password_set_at` and refreshes the token so the proxy sees it. "Came from an email link" is a positive list of `amr` methods (`signedInWithEmailLink`, `sessionFromEmailLink`); anything else fails closed. In the database, `private.session_uid()` is `auth.uid()` only for a trusted session, and every tenancy helper uses it, so an untrusted password token reads nothing. Companies are created only for trusted accounts; `/set-password` takes a new owner's name and company name (`createOwnerCompany`). Email links the app starts are capped per subject and per `x-real-ip` (`public.email_link_allowed`, secret key only). - Bank picker and account name check (`billing/bank-lookup.ts`, `billing/bank-check-schema.ts`, `people/bank-lookups.ts`, slice 2.3b): banks come from `src/lib/banks.ts` (code + name; the stored `bank_name` is the list's name). `runBankLookup` checks the bank, calls `begin_bank_account_lookup` with the secret key (role for the purpose; 30 an hour per user, 100 per company, `MLBL1`/`MLBL2`), asks the resolver, and records the answer with `finish_bank_account_lookup`; the number is stored only as `bankAccountDigest` (HMAC-SHA256 with a subkey of the personal data key, bound to company and bank code) and its last four. The resolver is Metalira's provider when `MONNIFY_API_KEY` and `MONNIFY_SECRET_KEY` are set (`MONNIFY_BASE_URL` sandbox or live; read only in this file), the deterministic test resolver outside production otherwise (labelled "Test lookup"; `METALIRA_TEST_BANK_LOOKUP=1` lets a local production build use it, never Vercel production), and a refusal in production without keys. At submit, `takeCheckedName` reads the caller's own lookup under RLS, checks it is fresh (30 minutes), unused, for this purpose, worker, bank and number, and recomputes the match (`src/lib/bank-name-match.ts`): no match refused, near match needs `nameCheckReason` (10+ characters). The insert triggers (`*_lookup`) repeat the binding checks (`MLBL3`-`MLBL6`), take the account name from the lookup, mark it used, and require a lookup for the company account from a signed-in user (`MLBL7`); a worker request without one is `not_checked` (the import). Screens recompute the match from stored names (`nameCheckView`), so it can't drift. Never log the number, the returned name or a provider response.
