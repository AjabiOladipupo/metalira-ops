# Server modules

Server-only logic, one folder per module: identity, people, sites, workforce, payroll, business, billing, revenue, projects.

- Code here must never be imported by client components. Start each file that touches secrets with `import "server-only";`.
- The Supabase secret key (`SUPABASE_SECRET_KEY`) is read only by `supabase/admin.ts` (`createAdminSupabase()`). It bypasses RLS, so prefer the user's own client (`createServerSupabase()` from `src/lib/supabase/server.ts`) and scope admin queries to an organisation yourself.
- Validate every input with Zod at the boundary. Table changes are audited by database triggers in the same transaction; record app-level events (for example `pii.reveal`) with `rpc("log_audit", ...)`.
- Identity (`identity/`): `getSession()` / `requireAppAccess(href)` read the signed-in user, their memberships and the active organisation (httpOnly `mo_org` cookie, honoured only for the user's own manager memberships). Every Server Action that writes goes through `mutate()` in `identity/mutate.ts`: role check, Zod parse, then the write with the user's own client so RLS applies; the database triggers audit the row change in the same transaction, and `event` adds an app-level entry through `log_audit`. Multi-row or money writes belong in one SQL function called from `run()`.
- Personal data (`crypto/pii.ts`, `people/pii-access.ts`): NIN, bank account numbers and RSA PINs are stored as `bytea` in `_enc` columns with a `_last4` sibling (`bank_account_last4`, `rsa_pin_last4`) so lists never decrypt. Write with `sealPii(value, ctx)` (returns `{ enc, last4 }`, `enc` ready for supabase-js) or `encryptPii` / `encryptPiiForDb`; read with `decryptPii(value, ctx)`, which accepts a Buffer or PostgREST's `\x…` hex text. `ctx` is `{ organisationId, table, column, rowId }` and is bound into the GCM tag, so a value moved to another column, row or organisation will not decrypt: generate the row id with `crypto.randomUUID()` before the insert, and re-encrypt (never copy bytes in SQL) when a value moves, for example when an approved bank-detail change is applied to `workers`. AES-256-GCM, random IV per value, key version byte first; the key is `PII_ENCRYPTION_KEY` (32 bytes, base64), read on first use and nowhere else, failing closed with `PiiKeyError` when missing. Show masked values with `src/lib/mask.ts` (`maskAccount`, `maskRsaPin`, `maskPhone`, `maskNin`, `ninStatus`). Unmask only through `revealPii({ organisationId, field, entity, entityId, reason })`, which takes the role from the session's membership in that organisation, reads the `_enc` column itself with the user's RLS client (`workers` or `bank_detail_changes`, filtered on id and organisation), checks `canSeePii(role, field)` (owner and hr: all; finance: bank account only; everyone else masked) and writes a `pii.reveal` audit row before returning the value. `src/server/crypto` may be imported only from `src/server/` (ESLint and `tests/unit/pii-key-boundary.test.ts`).
- People (`people/`, slice 1.3): `createWorker`, `updateWorker`, `addPayRate`, `cancelPayRate` and `endEmployment` in `people/workers.ts` (Zod schemas in `people/schemas.ts`) go through `mutate()` with roles owner, admin and hr. Multi-row writes are SQL functions running as the caller (`public.create_worker`, `public.add_pay_rate`, `public.cancel_pay_rate`, `public.end_employment`), so RLS and column grants still apply; each takes `p_organisation_id` (the active organisation from the mutate context) and touches only that organisation's rows, so a user with a role in two companies can't act on the other one's workers. Personal data is sealed with `sealPii` for the worker's row id (generated with `crypto.randomUUID()` before the insert). Money is sent to the database as strings of whole kobo, never JavaScript numbers, and read back the same way: select kobo columns cast to text (`basic_kobo::text`, `annual_rent_declared_kobo::text`) and convert with `koboFromText` (`people/pay-rates.ts`; `listPayRates` returns a worker's versions as `bigint` kobo). Never read a kobo column as the raw `number` the generated types suggest. A blank staff ID gets the next free ID in the company's pattern (`people/staff-id.ts`, default `EMP-0001`); a staff ID never changes once saved (no update grant) and is never reused, even after the worker leaves. The database enforces the rest: pay-rate versions in force are never updated except to close `effective_to` (a change is a new version from today or later, and `add_pay_rate` closes the previous one the day before); a scheduled version can have its amounts changed or be cancelled (`cancel_pay_rate`, latest version only, which reopens the version before it) but never moved, and the end of a version followed by another can't change, so versions never leave a gap; no overlapping versions; no pay rate before the start date; one line manager (`line_manager_worker_id` or `line_manager_membership_id`, never both, no loops); `needs_pay_details` kept up to date by trigger (bank details missing, or no rate in force on the later of today and the start date; payroll still resolves the rate as of each pay date); bank columns not updatable by signed-in users (slice 1.7 approvals); `memberships.worker_id` not updatable by signed-in users (slice 1.9 sets it at invite acceptance); and a `workers.personal_data` audit row naming which personal data fields changed, never the values. Database refusals arrive as SQLSTATE `MLPR1`-`MLPR3` (pay rates), `MLLM1`/`MLLM2` (line manager) and `MLAS1` (assignment client); `workers.ts` maps them to field errors.
